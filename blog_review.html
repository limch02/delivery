장바구니 기능 구현 후 코드 리뷰 회고

JPA DDD Spring Boot 리팩토링

장바구니 생성 및 수량 변경 기능을 구현하고 코드 리뷰를 받았다. 단순히 동작하는 코드를 넘어 설계 관점에서 많은 피드백이 있었고, 이를 고민하고 수정하는 과정에서 배운 내용을 정리한다.

1. LazyInitializationException의 발생 조건과 해결 방안

발생 조건

JPA의 연관관계는 기본적으로 FetchType.LAZY로 설정하는 것이 권장된다. LAZY 로딩은 실제로 해당 필드에 접근하는 시점에 DB 쿼리를 발생시킨다. 문제는 영속성 컨텍스트(트랜잭션)가 종료된 이후에 LAZY 필드에 접근하면 Hibernate가 프록시 객체를 초기화할 수 없어 LazyInitializationException이 발생한다. 

// Cart 엔티티
@OneToMany(mappedBy = "cart", cascade = CascadeType.ALL, orphanRemoval = true)
private List<CartItem> cartItems = new ArrayList<>();

// CartItem 엔티티
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "cart_id")
private Cart cart;

예를 들어 서비스 메서드가 @Transactional(readOnly = true)인데 응답 변환 시점에 cart.getCartItems()를 호출하면, 트랜잭션이 이미 닫혀 있어 예외가 발생한다.

해결 방안: JOIN FETCH

필요한 연관 데이터를 미리 한 번의 쿼리로 함께 가져오도록 JPQL에 JOIN FETCH를 사용했다. 

// CartRepository
@Query("""
    SELECT DISTINCT c
    FROM Cart c
    LEFT JOIN FETCH c.store
    LEFT JOIN FETCH c.cartItems ci
    LEFT JOIN FETCH ci.menu
    WHERE c.member.email = :email
    """)
Optional<Cart> findByMemberEmailWithItems(@Param("email") String email);
LAZY 로딩 자체가 나쁜 것이 아니라, 어디서 어떤 데이터가 필요한지 파악하고 그에 맞는 쿼리 메서드를 Repository에 정의하는 것이 핵심이다. N+1 문제도 이 맥락에서 함께 고민해야 한다.

2. 도메인 불변식(Domain Invariant)에 대한 고민

불변식이란

도메인 불변식이란 도메인 객체가 항상 지켜야 하는 규칙이다. 예를 들어 장바구니에는 하나의 가게 메뉴만 담을 수 있다는 규칙이 있다. 이 규칙이 깨지는 순간 데이터는 일관성을 잃는다.

문제: 불변식 검증이 서비스에만 노출

초기 구현에서는 다른 가게 메뉴를 담으려 할 때의 검증이 서비스 레이어에만 존재했다. 도메인 객체 자신은 자신의 상태가 유효한지 알지 못했다.

개선: 도메인 메서드로 불변식 수호

판단 로직을 도메인 메서드로 옮겨, Cart 객체가 스스로 불변식을 지키도록 했다. 

// Cart.java
public boolean hasDifferentStore(Long storeId) {
    return !store.getStore_id().equals(storeId);
}

// CartService.java
if (cart.hasDifferentStore(menu.getStoreId())) {
    throw new CartException(CartErrorCode.DIFFERENT_STORE);
}
서비스는 어떤 순서로 도메인을 호출할지만 알고, 도메인은 자신의 상태가 유효한지를 스스로 판단해야 한다.

3. 빈약한 도메인 모델 개선 및 Cascade 이해

빈약한 도메인 모델이란

도메인 객체가 데이터(필드)만 갖고 행위(메서드)가 없는 경우를 빈약한 도메인 모델(Anemic Domain Model)이라고 한다. 비즈니스 로직이 전부 서비스 레이어에 쌓이게 되며, 도메인 객체는 단순 DTO처럼 동작한다.

문제가 된 코드

장바구니에 메뉴를 추가하는 로직이 서비스에 직접 구현되어 있었다. 더불어 CascadeType.ALL이 설정되어 있음에도 cartItemRepository.save()를 명시적으로 호출하고 있었다. 

// Before - CartService
cart.findItemByMenuId(menu.getMenu_id())
    .ifPresentOrElse(
        existing -> existing.addQuantity(command.quantity()),
        () -> cartItemRepository.save(cart.addItem(menu, command.quantity()))
        //    ^^^^^^^^^^^^^^^^^^^
        //    CascadeType.ALL이 있는데 직접 save를 호출하는 중복
    );

CascadeType.ALL과 orphanRemoval 이해

CascadeType.ALL은 부모 엔티티(Cart)의 영속성 상태가 자식(CartItem)에 전파됨을 의미한다. Cart가 이미 영속 상태일 때 cart.getCartItems().add(cartItem)만 해도 CartItem은 자동으로 영속화되어 INSERT된다. cartItemRepository.save()는 불필요하다.

orphanRemoval = true는 부모 컬렉션에서 제거된 자식을 자동으로 DELETE한다. 수량이 1인 CartItem 제거 시 cart.getCartItems().remove(cartItem)만으로 DB에서도 삭제된다.

개선: 로직을 도메인으로 이동

// After - Cart.java
public void addMenu(Menu menu, int quantity) {
    findItemByMenuId(menu.getMenu_id())
        .ifPresentOrElse(
            existing -> existing.addQuantity(quantity),
            () -> this.cartItems.add(new CartItem(menu, quantity))
        );
}

// After - CartService
cart.addMenu(menu, command.quantity()); // 한 줄로 끝
"서비스가 도메인에게 일을 시키는 것"과 "서비스가 직접 일을 하는 것"의 차이를 명확히 인식하게 된 계기였다.

4. CartItem은 독립 엔티티가 아니다 — Aggregate Root를 통한 접근

문제: cartItemId로 직접 조회

수량 증가/감소 API의 초기 설계는 cartItemId를 경로 변수로 받아 CartItem을 직접 조회하는 방식이었다. 

// Before - Controller
PATCH /api/carts/items/{itemId}/increase
PATCH /api/carts/items/{itemId}/decrease

// Before - Service
private CartItem findCartItemWithOwnerCheck(String email, Long itemId) {
    CartItem cartItem = cartItemRepository.findByIdWithCartAndMember(itemId)
        .orElseThrow(() -> new CartException(CartErrorCode.CART_ITEM_NOT_FOUND));
    if (!cartItem.getCart().isCreatedBy(email)) {  // CartItem → Cart → Member 역방향 탐색
        throw new CartException(CartErrorCode.CART_ITEM_FORBIDDEN);
    }
    return cartItem;
}

두 가지 문제

  • 설계 문제: CartItem은 Cart 없이 독립적으로 존재할 수 없는 종속 엔티티다. 그런데 cartItemId로 직접 조회하면 CartItem이 독립 Aggregate인 것처럼 취급된다. DDD 관점에서 Cart가 Aggregate Root이므로, CartItem 접근은 Cart를 통해야 한다.
  • 역방향 체이닝 문제: CartItem 자체는 Member와 직접 연관이 없다. 그런데 소유자 검증을 위해 cartItem.getCart().isCreatedBy(email)처럼 CartItem → Cart → Member 방향으로 역으로 거슬러 올라가는 코드가 생겼다. 이는 의존 방향이 뒤집힌 코드로, 불필요한 JOIN을 유발하고 읽기도 어렵다.

해결: cartId + menuId로 Cart를 먼저 조회

Cart 내에서 동일 메뉴는 CartItem 하나로만 존재한다(addMenu 로직으로 보장). 따라서 cartId + menuId 조합으로 CartItem을 유일하게 특정할 수 있다. 

// After - Controller
PATCH /api/carts/{cartId}/items/{menuId}/increase
PATCH /api/carts/{cartId}/items/{menuId}/decrease

// After - Service
private Cart findCartWithOwnerCheck(String email, Long cartId) {
    Cart cart = cartRepository.findByIdWithItemsAndMember(cartId)
        .orElseThrow(() -> new CartException(CartErrorCode.CART_NOT_FOUND));
    if (!cart.isCreatedBy(email)) {  // Cart 선에서 바로 검증 완료
        throw new CartException(CartErrorCode.CART_ITEM_FORBIDDEN);
    }
    return cart;
}

public CartItemResult increaseCartItemQuantity(String email, Long cartId, Long menuId) {
    Cart cart = findCartWithOwnerCheck(email, cartId);
    CartItem cartItem = cart.findItemByMenuId(menuId)
        .orElseThrow(() -> new CartException(CartErrorCode.CART_ITEM_NOT_FOUND));
    cartItem.increaseQuantity();
    return CartItemResult.from(cartItem);
}
4번(직접 조회)과 5번(역방향 체이닝)은 같은 뿌리에서 나온 문제였다. CartItem을 직접 조회하다 보니 소유자 검증을 위해 역방향으로 올라가는 코드가 생겼고, Cart를 먼저 조회하는 구조로 바꾸자 역방향 탐색도 자연스럽게 사라졌다.

5. 양방향 연관관계를 단방향으로 리팩토링

기존 양방향 구조

// Cart
@OneToMany(mappedBy = "cart", cascade = CascadeType.ALL, orphanRemoval = true)
private List<CartItem> cartItems;

// CartItem
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "cart_id", nullable = false)
private Cart cart;

문제: CartItem이 Cart를 알아야 할 이유가 없다

4번 리팩토링을 통해 cartItem.getCart()를 호출하는 코드가 모두 사라졌다. CartItem의 cart 필드는 JPA FK 관리 용도로만 남은 상태였다.

양방향 연관관계는 편리하지만 관리 비용이 있다. 양쪽이 서로를 참조하므로 어느 쪽이 FK 주인인지 항상 인지해야 하고, 불필요한 역방향 탐색의 여지가 생긴다. 사용하지 않는 방향을 유지하는 것은 불필요한 복잡도다.

개선: Cart → CartItem 단방향

// Cart - @JoinColumn을 Cart 쪽에서 직접 관리
@OneToMany(cascade = CascadeType.ALL, orphanRemoval = true)
@JoinColumn(name = "cart_id", nullable = false)
private List<CartItem> cartItems = new ArrayList<>();

// CartItem - cart 필드 완전히 제거
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "menu_id", nullable = false)
private Menu menu;

public CartItem(Menu menu, int quantity) {
    this.menu = menu;
    this.quantity = quantity;
}

트레이드오프

단방향 @OneToMany + @JoinColumn은 INSERT 시 Hibernate가 FK를 별도 UPDATE 쿼리로 처리한다. 양방향에서는 CartItem INSERT 한 번에 FK가 설정되지만, 단방향에서는 INSERT 후 UPDATE가 추가된다. 장바구니 특성상 삽입 빈도가 낮고 성능 임계치에서 멀기 때문에 감수할 만한 트레이드오프다.

양방향 연관관계가 반드시 나쁜 것이 아니다. 하지만 실제로 양쪽 탐색이 모두 필요한가를 먼저 물어야 한다. 필요 없는 방향을 제거하면 도메인 모델이 단순해지고, 의존 방향이 명확해진다.

마무리

이번 리뷰를 통해 단순히 "동작하는 코드"와 "좋은 코드"의 차이를 실감했다. 핵심은 하나였다. 객체가 스스로의 책임을 지도록 설계하는 것. Cart가 Aggregate Root로서 CartItem을 관리하고, 도메인 규칙은 도메인 메서드가 수호하며, 서비스는 흐름만 조율하는 구조가 되니 코드가 읽히고 변경이 한 곳으로 모였다.
