직접 겪으면서 배운 객체지향 설계 원칙들

배달 서비스 프로젝트를 진행하면서 코드 리뷰를 통해 여러 설계 원칙들을 직접 경험했습니다. 책에서 읽은 원칙을 내 코드에서 발견하는 것은 또 다른 느낌이었습니다. 제가 실제로 위반했던 코드와 수정 과정을 원칙별로 정리해봤습니다.

📎 프로젝트 GitHub: https://github.com/limch02/delivery

1. SRP — 단일 책임 원칙 (Single Responsibility Principle)

클래스는 하나의 책임만 가져야 한다는 원칙입니다. 하나의 이유로만 변경되어야 한다고도 표현합니다.

사례 1 — 서비스가 변환 책임까지 가졌던 문제

처음에 MemberService 안에 도메인 객체를 Result DTO로 변환하는 메서드가 있었습니다.

// 수정 전
public class MemberService {
    private SignUpResult toResult(Long id, String email, String phoneNum, Role role, String address) {
        return new SignUpResult(id, email, phoneNum, role, address);
    }
}

서비스의 책임은 비즈니스 로직을 처리하는 것입니다. 객체를 변환하는 것은 서비스의 관심사가 아닙니다. 변환 책임은 DTO 자신이 정적 팩토리 메서드로 가져가는 것이 적절합니다.

// 수정 후 — 변환 책임을 Result DTO가 가짐
public record MemberResult(String email, String phoneNum, String address) {
    public static MemberResult from(Member member) {
        return new MemberResult(member.getEmail(), member.getPhone_num(), member.getAddress());
    }
}

사례 2 — 비밀번호 검증을 서비스가 직접 하던 문제

서비스에서 비밀번호 일치 여부를 직접 판단하고 예외를 던지고 있었습니다.

// 수정 전
if (!passwordEncoder.matches(command.password(), member.getPassword())) {
    throw new MemberException(MemberErrorCode.INVALID_PASSWORD);
}

"비밀번호가 맞는지 아는 것"은 Member 도메인이 자신의 상태를 검증하는 책임입니다. 서비스가 이 로직을 갖고 있으면 도메인 로직이 서비스 밖으로 새어나온 것입니다.

// 수정 후 — 검증 책임을 Member 도메인에 위임
member.validatePassword(passwordEncoder.matches(command.password(), member.getPassword()));

// Member.java
public void validatePassword(boolean isValid) {
    if (!isValid) {
        throw new MemberException(MemberErrorCode.INVALID_PASSWORD);
    }
}

2. OCP — 개방-폐쇄 원칙 (Open-Closed Principle)

확장에는 열려있고, 수정에는 닫혀있어야 한다는 원칙입니다. 새로운 기능을 추가할 때 기존 코드를 수정하지 않아야 한다는 의미입니다.

사례 — GlobalExceptionHandler의 switch 분기

// 현재 코드
HttpStatus status = switch (e.getMemberErrorCode()) {
    case DUPLICATE_EMAIL -> HttpStatus.CONFLICT;
    case MEMBER_NOT_FOUND -> HttpStatus.NOT_FOUND;
    case INVALID_PASSWORD, UNAUTHORIZED -> HttpStatus.UNAUTHORIZED;
};

새로운 ErrorCode가 추가될 때마다 GlobalExceptionHandler를 직접 열어서 case를 추가해야 합니다. 이는 OCP 위반입니다.

해결 방법으로 ErrorCode 인터페이스에 getHttpStatus()를 추가하는 방법을 고려했습니다. 그러면 새로운 ErrorCode가 생겨도 handler를 수정할 필요가 없습니다. 하지만 이렇게 되면 도메인 레이어의 ErrorCode가 presentation 레이어의 관심사인 HttpStatus를 알게 되어 레이어 의존 방향이 역전됩니다.

OCP를 지키면 레이어 의존 방향이 깨지고, 레이어 의존 방향을 지키면 OCP를 일부 포기해야 하는 트레이드오프가 존재합니다. 현재는 레이어 의존 방향을 우선해서 switch 구조를 유지하고 있습니다.

3. DIP — 의존성 역전 원칙 (Dependency Inversion Principle)

구현체가 아닌 추상화(인터페이스)에 의존해야 한다는 원칙입니다. 고수준 모듈이 저수준 모듈에 직접 의존하면 안 됩니다.

사례 — PasswordEncoder 인터페이스 위치 문제

처음에 PasswordEncoder 인터페이스와 구현체 BcryptPasswordEncoder가 모두 infrastructure 레이어에 있었습니다.

// 수정 전 — 인터페이스가 infra에 있어 service → infra 의존 발생
import com.delivery.member.infrastructure.PasswordEncoder;

public class MemberService {
    private final PasswordEncoder passwordEncoder; // infra를 직접 의존
}

서비스가 인터페이스를 통해 사용하더라도 import 경로가 infrastructure라면 결국 상위 레이어가 하위 레이어를 의존하는 구조입니다. 인터페이스를 application 레이어의 port로 이동시켜 의존 방향을 바로잡았습니다.

// 수정 후 — 인터페이스를 application/port로 이동
import com.delivery.member.application.port.PasswordEncoder;

// application/port/PasswordEncoder.java
public interface PasswordEncoder {
    String encode(String rawPassword);
    boolean matches(String rawPassword, String encodedPassword);
}

// infrastructure/BcryptPasswordEncoder.java
public class BcryptPasswordEncoder implements PasswordEncoder { ... }

이렇게 하면 구현체가 BCrypt에서 다른 방식으로 바뀌어도 서비스 코드는 수정할 필요가 없고, 테스트 시 mock으로 쉽게 대체할 수 있습니다.

4. Law of Demeter — 디미터 법칙

직접 아는 객체하고만 대화하라는 원칙입니다. 메서드 체이닝으로 다른 객체의 내부를 탐색하는 것은 위반입니다.

사례 — menu.getStore().validateOwner()

메뉴 수정/삭제 시 소유자 검증을 이렇게 작성했습니다.

// 수정 전 — Menu를 통해 Store에 접근
menu.getStore().validateOwner(email);

이 코드는 서비스가 Menu의 내부 구조(Store를 가지고 있다는 것)를 알아야 합니다. Menu가 바뀌면 이 코드도 영향을 받습니다.

URL의 path variable에서 storeId를 직접 받아 Store를 조회하고, store.validateOwner(email)을 호출하는 방식으로 변경했습니다.

// 수정 후 — storeId로 Store를 직접 조회 후 검증
Store store = storeRepository.findByIdWithOwner(storeId)
        .orElseThrow(() -> new StoreException(StoreErrorCode.STORE_NOT_FOUND));

store.validateOwner(email);

Menu menu = menuRepository.findByIdAndStoreId(menuId, storeId)
        .orElseThrow(() -> new MenuException(MenuErrorCode.MENU_NOT_FOUND));

5. Tell, Don't Ask

객체에게 상태를 물어보고 외부에서 판단하지 말고, 객체에게 직접 행동을 시키라는 원칙입니다. 디미터 법칙과 연결되는 개념입니다.

사례 — 소유자 검증 로직의 중복

처음에 소유자 검증이 서비스에 직접 작성되어 있었습니다.

// 수정 전 — 서비스가 Store의 상태를 물어보고 직접 판단
if (!store.getOwner().getEmail().equals(email)) {
    throw new StoreException(StoreErrorCode.NOT_STORE_OWNER);
}

서비스가 Store의 내부 상태(owner의 email)를 꺼내서 직접 비교하고 있습니다. 이 로직이 여러 메서드에 중복되면 수정 시 모두 찾아서 바꿔야 합니다.

"소유자가 맞는지 검증하라"는 행동을 Store에게 직접 시키는 방식으로 변경했습니다.

// 수정 후 — Store에게 직접 시킴
store.validateOwner(email);

// Store.java
public void validateOwner(String email) {
    if (!this.owner.getEmail().equals(email)) {
        throw new StoreException(StoreErrorCode.NOT_STORE_OWNER);
    }
}

검증 로직이 도메인 안으로 들어가면서 서비스 코드가 단순해지고, 수정이 필요할 때 한 곳만 바꾸면 됩니다.

6. 레이어 의존 방향

SOLID나 디미터 법칙과 별개로, 레이어드 아키텍처에서 반드시 지켜야 하는 것이 의존 방향입니다. 의존은 항상 위 → 아래 방향으로만 흘러야 합니다.

사례 1 — 상위 레이어 DTO를 하위 레이어에서 사용

// 수정 전 — service가 presentation DTO를 직접 받음
public SignUpResponse signUp(SignUpRequest request) { ... }

SignUpRequest, SignUpResponse는 presentation 레이어의 DTO입니다. 하위 레이어인 service가 이를 알면 의존 방향이 역전됩니다. controller에서 SignUpCommand로 변환 후 전달하는 방식으로 수정했습니다.

사례 2 — ErrorCode에 HttpStatus를 담은 문제

// 수정 전 — domain 레이어 enum이 HttpStatus를 가짐
DUPLICATE_EMAIL(HttpStatus.CONFLICT, "이미 사용 중인 이메일입니다."),

HttpStatus는 presentation 레이어의 관심사입니다. domain의 ErrorCode가 이를 알면 하위 레이어가 상위 레이어를 의존하게 됩니다. HttpStatus 매핑은 GlobalExceptionHandler에서 담당하도록 이동했습니다.

마치며

이 원칙들을 처음 접했을 때는 다소 추상적으로 느껴졌습니다. 하지만 직접 위반한 코드를 작성하고, 리뷰를 통해 문제를 발견하고, 수정하는 과정을 거치면서 각 원칙이 왜 존재하는지 체감할 수 있었습니다.

원칙들이 항상 함께 지켜지는 것은 아닙니다. OCP와 레이어 의존 방향처럼 충돌하는 경우도 있고, 그럴 때는 현재 상황에서 무엇이 더 중요한지 판단하는 것이 필요합니다. 원칙을 아는 것보다 트레이드오프를 인식하고 선택하는 것이 더 중요하다고 생각합니다.
